# RG351P 原生 2D 格斗引擎方案调研

2026-11-03。方案与取舍记录；标准 libretro 软件 POC 已实现，实现、验证和后续计划见 [格斗文档](fighter.md)，已有 boot-0015 的合成负载结果，真实素材与长期稳定性仍待验收。

## 目标和结论

按已经确认的方向：480×320，拳皇式传统横版 1 对 1 格斗，以拳皇、侍魂等角色跨作品对战为内容方向。场景只需要背景、共同地面和左右边界；可以有简单横向镜头，不做平台、关卡探索、出界淘汰或四人同场。“大乱斗”指角色跨作品集合，不指任天堂大乱斗的规则。拳皇式操作与拳皇的三人轮换队制是两回事，首版先做单人对单人。

**建议自研小型 C 引擎，采用数据驱动角色、60 Hz 固定逻辑和 CPU 软件精灵渲染，接入现有前端。** 先用两个测试角色建立完整对局，再接入一个拳脚型和一个持刀型角色，验证跨作品的规则适配。桌面端提供开发运行器，设备端复用 KMS、音频、输入、电源和日志。

MUGEN 的主要借鉴点是角色、动画、招式与背景可独立制作。首版不承诺任意 MUGEN 人物包直接运行；这会把工作重心从格斗玩法转到兼容已有脚本的细节。如果未来“下载人物包就能玩”变成首要需求，应重新比较 IKEMEN GO 移植和自研，而不是在当前方案上无限增加兼容补丁。

## 当前设备和代码的实际约束

本节依据仓库代码、[硬件资料](hardware-research.md)及[真机记录](roadmap.md)，不是通用掌机配置推测。

| 项目 | 当前情况 | 对方案的影响 |
|---|---|---|
| CPU / 内存 | RK3326，四核 Cortex-A35，最高约 1.3 GHz，1 GiB 内存 | 两个角色的逻辑规模可控；主要风险是精灵混合、资源加载和帧调度，仍须真机测量 |
| 显示 | 逻辑 480×320，物理扫描 320×480，RGB565 KMS 双缓冲 | 先在缓存画布合成，再旋转写扫描缓冲；不要直接在扫描缓冲反复读改写 |
| GPU | 内核没有 Panfrost，DTS 关闭 GPU，当前系统没有 Mesa/EGL | GPU 引擎不是直接链接就能用，需额外的系统移植和功耗验证 |
| 用户态 | 静态 musl，前端是 PID 1，没有桌面、shell、常规服务 | 复用现有宿主最省集成成本；游戏核心不能承担系统退出和关机 |
| 输入 | `input.c` 汇总按键，`core.c:input_state()` 仅提供 port 0 | 足够先做内置手柄对 CPU；双人本地对战需要独立手柄分配，不能直接插上就假定可用 |
| 时间 | 游戏循环当前每个 vblank 跑一次核心 | 新游戏应显式决定 60 Hz 与实际屏幕刷新率的同步方式，不能继承 GBA 时序假设 |
| 音频 | tinyalsa、重采样、缓冲与调频已经存在 | 可以复用输出；格斗游戏仍需专门测输入响应和音效延迟 |
| 调试 | 无串口，靠 GBA 分区 `log/boot-NNNN/` | 错误、资源信息、帧耗时与复现输入必须能从一次日志取回 |

已有视频核心证明非 GBA 内容可以接入同一前端，但当前 ROM 识别、菜单、特效和存档仍有 GBA 专用分支，增加核心不等于自动完成产品集成。尤其不能给格斗画面默认套 GBA 色彩校正、LCD 网格或帧混合。

## 可选路线

| 路线 | 优点 | 对本项目的成本 | 判断 |
|---|---|---|---|
| 自研 C 小型引擎 | 可直接适配静态构建、现有软件显示；规则和资源预算完全可控 | 战斗、AI、角色工具都要做，人物制作是长期工作 | 推荐，适合设备优先与精选角色 |
| 移植 IKEMEN GO | 已有 MUGEN 资源兼容和成熟格斗功能，MIT 引擎许可 | Go 与原生库、图形后端和现有 musl 系统都要整合；需要另测设备性能 | 若完整人物包兼容最重要，这是更值得先验证的路线 |
| 基于 OpenBOR | 有 2D 动作、精灵、脚本和 ARM64 构建经验 | 以横版清关为主要方向；仍须调整传统格斗规则，也不提供 MUGEN 行为兼容 | 用户已明确传统对战，不作为首选 |
| 使用通用引擎 | 编辑器和资产管线较成熟 | 需另评估静态用户态、图形栈和设备输出；不自动提供格斗规则 | 当前无必要为小型 2D 引擎引入整套框架 |

IKEMEN GO 官方构建文档列出 Linux ARM64 构建路径，以及 SDL2、FFmpeg、libxmp 等依赖；因此 ARM64 本身不是否决理由。[官方构建说明](https://github.com/ikemen-engine/Ikemen-GO/blob/develop/BUILDING.md)

其当前 README 列出的图形需求包括 OpenGL / OpenGL ES / Vulkan；这与本仓库没有 GPU 用户态的配置存在直接差异。文档同时存在旧图形回退说明，实际移植必须固定具体版本、后端和依赖，不能据此宣称 RG351P 已可用或一定跑不动。[官方仓库与要求](https://github.com/ikemen-engine/Ikemen-GO)

OpenBOR 官方将自身定位为横版动作引擎，当前构建指南也列出 ARM64；这里不选它是玩法与宿主整合的取舍，不是断言它不能实现对战。[官方仓库](https://github.com/DCurrent/openbor)、[构建指南](https://github.com/DCurrent/openbor/blob/master/COMPILING.md)

以上是适配成本判断，没有在此设备上跑过这些引擎的基准。

## 首版玩法范围

- 一个背景，一条地面，两名角色，血量归零或时间结束判胜，支持重新对战和返回选择页。
- 移动、蹲下、前后跳、站防与蹲防；普通技、一个指令必杀、一次投技、一种倒地起身。
- 拳皇风格四攻击键，按角色配置拳脚或斩击语义。首版不同时追求多个年代作品的逐帧还原。
- Hitstop（打击停顿）、受击硬直、防御硬直、击退、击倒、取消窗口、基本浮空限制，形成完整手感链条。
- 首先内置手柄对 CPU，训练模式可以查看判定框、招式状态和输入历史。
- 初期不做联网、三人轮换、援护、复杂超必杀演出、武器掉落与拾取；双人 USB 手柄作为独立后续阶段。

拳皇与侍魂应使用同一个战斗内核，角色数据描述攻击距离、伤害、硬直、移动与资源。拳皇的快节奏连段和侍魂的长距离重击不能只靠导入图片自然共存，需要明确统一规则并重新平衡。建议首版共用一套血量、基础防御和取消规则，角色特色逐个增加；怒气、爆气、弹刀等系统以后按模块实现。

## 引擎结构与集成

当前目录与预留扩展如下：

```text
app/fighter/            战斗逻辑、动画、指令识别、AI、软件渲染、资源读取
app/fighter/libretro.c  标准 libretro API，设备静态链接，桌面生成动态 core
app/fighter-host/       可选的测试宿主；日常桌面验证优先用 RetroArch
tools/fighter/          资源编译、校验、报告工具
```

核心接口保持小：加载资源包、输入一帧、推进一个 tick、取得画面和声音、序列化状态。文件读写、日志和资源访问通过宿主接口传入，战斗代码不直接调用 DRM、evdev 或电源管理。核心用 C，桌面和设备都链接同一份逻辑；桌面首先通过 RetroArch 加载动态 core，无需先实现 SDL 宿主。

设备优先采用现有 `core_api` 适配器，输出 480×320 RGB565 与立体声 PCM。启动入口可先增加一个格斗游戏包类型，当前使用 `.fight` 二进制测试包，前端已识别；最终角色资源格式仍需完善。适配时需要检查 `cores.c`、`core.c`、`settings`、`romlist`、菜单和即时存档识别，不把新游戏伪装成 `.gba`。

系统菜单保留 SELECT+START，START 可给游戏暂停；电源、音量、休眠和关机继续由前端处理。首版设置只显示本游戏支持的项目。恢复状态包含资源版本摘要，人物包变化时拒绝恢复旧对局，并记录原因。

## 战斗时间与输入

固定 60 Hz 逻辑，每 tick 约 16.667 ms。速度、判定、指令窗口和动画时长都使用 tick，不依赖渲染帧率；暂停时不推进战斗。使用定点位置和速度（例如 16.16），乘法用足够宽的中间值，规定舍入和溢出范围。确定性来自完整设计，不只是采用整数。

建议每 tick：采样输入并更新指令历史 → 玩家及 AI 决策 → 状态与动画推进 → 移动和推挤 → 收集攻击命中 → 按明确规则统一结算 → 音效和画面事件。双方攻击先收集再结算，使同帧相打不取决于角色更新顺序；投技、无敌、打击停顿和倒地必须有明确优先级。

保留固定长度输入环，分别记录按下、保持、松开和方向，支持斜向、蓄力、同时按键与动作优先级。面向改变时定义历史方向的解释方式，避免跳到背后导致同一段输入被错误重解释。先支持一种宽容度参数，不堆叠自动连招。

方向相反同时输入的处理、输入缓冲、招式取消和 Hitstop 中能否读指令都必须写进规则，并能通过回放重现。AI 产出同样的玩家输入，难度通过反应延迟、出招选择和失误概率调整，避免直接绕过操作规则。

libretro core 声明 60 Hz，每次 retro_run 推进一个 tick，不自行读取墙钟追赶或睡眠。实际屏幕刷新率由宿主处理：本机前端从 KMS 读取，必要时协调核心调用与显示重复/丢弃，并限制追赶。音频按逻辑时间产生，宿主适配设备时钟；需要审查当前每 vblank 调用一次核心的节奏。

## 背景、精灵与 480×320 构图

逻辑画布固定 480×320，玩法坐标独立于设备旋转。背景首版用一张静态图，可以加少量动画；地面只是一条高度参数，不是物理场景。可先固定镜头，只有角色间距和屏幕边缘需要时再加有限横向滚动。首版避免连续缩放镜头，保持像素稳定。

人物按各自原始像素比例导入，统一脚底锚点和世界尺度。两个角色身高、攻击距离和 HUD 占用须在实机看，不能把所有角色图片强拉成同尺寸。用户已确定跨作品角色按原作像素 1:1 显示，接受 KOF 与侍魂等系列之间的身高差异，除非有不损失像素质量的完美方案，否则不做缩放。原作品画面、素材像素和 480×320 的比例通常不同，背景应重新排版或裁切；不要把整个旧游戏画面直接拉满新屏幕。碰撞盒跟随角色与动画帧，不能从透明图片外接矩形推导。

软件渲染路线：缓存内存里的 RGB565 画布 → 背景和角色逐层合成 → HUD / 特效 → 旋转拷贝到 KMS 后缓冲 → page flip。优先支持索引色精灵、透明色、调色板、裁剪和水平翻转；离线编译不透明片段以跳过透明区域。半透明和加法混合只用于受预算约束的小特效，普通人物不需要逐像素 alpha 混合。

资源在选人或加载界面解压和准备，当局常驻；禁止战斗中从 SD 卡临时解压下一张招式图。先用标量 C 正确实现和测量，瓶颈确认后再优化热点或增加 NEON，不先写平台专属汇编。

## 角色资源和 MUGEN 兼容边界

MUGEN 人物的行为依赖 CNS 状态、触发条件、命中定义及对手状态等语义。官方 CNS 文档展示的执行顺序和状态控制说明：解析文件只是兼容的第一步。[Elecbyte CNS 文档](https://www.elecbyte.com/mugendocs/cns.html)

建议将编辑用文本与运行包分开：主机工具读取角色描述、图片、声音，检查后生成版本化二进制资源包；设备只读取受控包。文本可用 JSON，运行时无需引入通用脚本解释器。普通招式用状态、帧事件和条件表表达；出现确实难表达的招式时再决定是否需要小型字节码，首版不设计通用语言。

| 层次 | 内容 | 优先级 |
|---|---|---|
| 原生人物格式 | 元数据、精灵、调色板、锚点、动画、攻击/受击/推挤框、招式、音效 | 首版 |
| 外部素材导入 | 将明确支持的图片、音频转换为本引擎资源 | 首版 |
| MUGEN 素材转换 | 后续选择特定 SFF/SND/AIR 版本实现离线转换；逐项验证格式 | 可选，当前未验证全部格式细节 |
| MUGEN 指令与行为 | CMD / CNS 的有限子集，限定测试角色并报告不支持项 | 后期独立决策 |
| 任意人物包兼容 | Helpers、Projectile、自定义受击状态、复杂表达式及历史行为差异 | 不作为当前目标 |

导入工具必须输出版本、精灵数、内存估计、缺失资源和不支持特性。遇到不支持的行为要拒绝或明确要求人工改写，不能悄悄跳过后称人物已经兼容。直接读取商业 ROM 并自动生成完整人物，不在本方案范围内。

首个测试包用自制占位素材；随后直接用原作提取素材验证流程。用户已确定版权暂不考虑，原作素材可以提交进仓库和镜像，将来统一清洗。引擎源码和人物/音乐/背景分别记录来源与许可，第三方包不默认放进发行镜像。角色行为需要逐招制作、调试和平衡，通常比显示出人物更耗时；引擎完成不等于已有完整拳皇与侍魂角色库。

## 性能预算与一次上机能回答的问题

以下是初始验收目标，不是测量结果：

| 项目 | 初始预算 / 验收 |
|---|---|
| 战斗、指令、AI | 每 tick 约 2 ms 以内 |
| 精灵、背景、HUD 合成 | 约 5 ms 以内 |
| 旋转与提交 | 约 2 ms 以内 |
| 混音和其余 CPU 工作 | 约 1 ms 以内 |
| 余量 | 帧内保留约 6.7 ms，覆盖调度、资源复杂度和峰值 |
| 总体 | 稳态总 CPU 工作 p99 < 12 ms，正常战斗无持续 missed vblank 或 underrun |
| 内存 | 先以游戏新增常驻资源与状态合计 ≤128 MiB 为资源预算，记录整个进程峰值 RSS |

这些预算按同一帧 CPU 工作统计，不把等待 vblank 算进去；须同时看最大值和连续超时，不只看平均。60 Hz 下单张 RGB565 画布约 300 KiB，单次全屏写入约 18.4 MB/s；这只说明基础像素规模，不包含透明精灵读取、混合、旋转、扫描输出及缓存代价，不能据此保证 60 fps。

真机压力测试至少覆盖：静态背景、双方移动、双方连续攻击、近距离重叠、投技、倒地、多个火花与飞行道具，持续 10 分钟观察温度和降频。记录各阶段 avg / p95 / p99 / max、missed vblank、underrun、CPU 频率、RSS、温度与电池功耗。先在最高频率确定上限，再逐档降低测试可持续性能，最后决定调频策略。桌面和 qemu 只验证功能，不能推算真机毫秒数。

输入延迟用高速摄像测按键到画面响应，日志只辅助分解采样、tick 和提交时间；USB 轮询和面板延迟不能由日志完整测出。音效延迟也需实际听测/录制，现有为模拟器准备的缓冲不能直接视作格斗游戏的最终参数。

每次加载记录引擎/包版本、摘要、人物和背景、精灵内存、音频格式、逻辑频率和屏幕刷新率。默认只写加载、异常和对局汇总；调试模式每 10 秒写聚合性能，支持保存最近若干秒输入与随机种子，不每 tick 刷日志。回放以资源摘要、初始状态、输入和随机种子为依据；状态校验应对规范化字段做哈希，不直接哈希含 padding 或指针的 C 结构体。

## 分阶段实施与退出条件

| 阶段 | 交付 | 通过条件 |
|---|---|---|
| P0：实机验证 | 两个占位精灵、一个背景、输入移动、声音和压力场景；最小设备适配 | 480×320 正确、运行 10 分钟，性能日志足以判定 CPU 路线是否留有余量 |
| P1：完整最小对局 | 两个测试角色、普通技/必杀/投技、防御受击倒地、简单 AI、胜负和训练显示 | 可从开始打到结束并重新开始，关键规则有可复现回放 |
| P2：跨作品角色样例 | 一个拳脚型、一个持刀型人物，原生资源工具与招式数据 | 锚点、判定、手感与不同角色尺度可用；逐招检验，真机压力验收 |
| P3：系统整合 | 选人、背景选择、菜单、休眠、保存恢复、错误包处理 | 退出与关机可靠，换包不会误恢复旧状态，GBA 和视频功能无回归 |
| P4：按需要扩展 | 更多人物、更多特色系统、双 USB 手柄、有限素材导入 | 每项单独定义规则和预算后实施 |

P0 不达标时先区分资源过大、旋转写入、alpha 混合或调频问题，再决定优化；只有软件路线确实缺乏余量时，才做启用 Panfrost/EGL 的独立实验，并比较功耗和系统成本。不要一开始同时维护两个设备渲染后端。

P1 的回放验证至少覆盖相打、跳跃换边、指令优先级、投技与无敌、Hitstop 输入、取消窗口和倒地恢复；P3 再覆盖坏资源、截断存档、休眠唤醒和资源版本变化。所有实际代码阶段按项目要求跑 `make image` 与 `make frontend-test`，零 warning 后才提交。

## 其他设备的兼容空间

现在就保留：平台无关战斗内核、独立逻辑画布、可配置按键、宿主音视频接口、明确端序和版本的资源包、固定 tick 与可序列化状态。其他比例屏幕先按比例缩放加黑边，不改变战斗范围和判定。旋转只在输出后端处理。

暂时不投入：通用插件系统、移动端触控、多分辨率 HUD、自适应场景、网络回滚与通用脚本虚拟机。确定性状态和输入回放对开发调试已经有价值，也为以后扩展留下空间，但不等于首版已支持联网。

## 补充决定：标准 libretro core 与可替换渲染器

用户明确不需要 MUGEN 兼容；可以参考相关开源实现，素材优先保持原作像素、版本和动作，原版提取图集与人物包都是候选来源。参考代码时记录项目许可。无需为未来完整 MUGEN 行为兼容预先设计运行时。

正式交付是标准 libretro core：同一源码在 RG351P 构建静态库（按现有流程重命名 retro_* 符号），在桌面构建动态库供 RetroArch 加载。实现加载/卸载、reset、run、输入、音视频与 serialize/unserialize；内容包作为 content 加载。支持 port 0/1 的逻辑输入，本机前端当前仅支持 port 0，双人设备映射仍需后续完善。使用 libretro 日志和可用的 VFS 接口，缺失时提供明确回退；存档不包含指针、GPU 句柄或文件描述符。资源路径、格式版本与缺失文件错误都需可诊断。参见 [libretro 开发文档](https://docs.libretro.com/development/cores/developing-cores/)。

软件路径先协商 RGB565，其他宿主若不接受可提供 XRGB8888 输出；480×320 画面通过 video callback 交给宿主，核心不自行旋转为 RG351P 面板方向。声明 60 Hz 和固定音频采样率，例如 48 kHz 时每 tick 800 个立体声采样帧。由宿主管节奏，核心每次 retro_run 恰好推进一个逻辑 tick，保证回放不依赖宿主墙钟。

战斗状态生成一份有序绘制指令，字段仅包括纹理/精灵 ID、源矩形、目标位置与尺寸、翻转、调色板、颜色、混合方式与裁剪。渲染器统一定义透明色、最近邻采样、混合与绘制顺序；软件与 GPU 共用资源源数据和这份语义，各自生成缓存。保存状态只保存战斗与动画状态，绘制指令和后端缓存可重建。

初期只实现 software 后端；标量 C 和 NEON 是该后端内部优化。将来可增加 GLES/OpenGL 后端，在支持的宿主通过 SET_HW_RENDER 协商上下文并处理 context_reset/context_destroy。这不是把最终软件帧上传 GPU，而是由 GPU 完成精灵合成。当前本机前端没有硬件渲染接口，还需要系统 GPU 驱动、EGL/GBM 等宿主设施，不能仅靠 core 选项启用。参见 [libretro 硬件渲染文档](https://docs.libretro.com/development/cores/opengl-cores/)。

后端选择在加载内容时确定；未来可提供 auto/software/hardware 选项，修改后重载内容，不承诺对局中热切换。auto 在上下文协商失败时可选软件；显式 hardware 失败则清楚报告原因。跨后端核对相同输入的战斗状态哈希以及画面位置、遮挡、调色板、混合效果，允许事先定义的颜色量化差异。

首轮合成负载真机结果表明，两人基础场景和有限特效可约 60fps，大量混合精灵会超时；原尺寸原作资源仍未验收。P0 必须使用接近真实规模的角色帧和最坏特效场景，分别测逻辑、软件合成、旋转提交和音频；占位方块的成绩不足以通过验收。若核心合成慢才考虑 GPU 后端；若瓶颈在旋转、调频、音频或宿主调度，优先修对应环节。先保留接口，避免在性能证据出现前同时维护多条完整路径。
