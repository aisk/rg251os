# 格斗引擎：POC 实现、验证和后续计划

2026-11-03。设备优先的 480×320、1 对 1、标准 libretro 软件渲染原型。当前交付用于验证核心和宿主集成；已完成首轮合成负载真机测试，普通场景可满速，高压力场景超时；P0 的持续稳定性与真实素材验收、原作素材导入以及 P1 的完整格斗规则仍待完成。设计取舍见[方案调研](fighting-engine-research.md)，数值、属性和多作品体系的设计见[数值设计](fighter-stats.md)，背景、打击效果和声音的设计见[表现层设计](fighter-presentation.md)，方案包含未来设计，实际完成范围以本文和代码为准。

## 目标和约束

- 自研拳皇式传统横版 1 对 1，以拳皇、侍魂等跨作品角色对战为方向。只需背景、共同地面与左右边界；不做平台规则，不考虑四人。
- 无需兼容 MUGEN 人物行为。可以参考 MUGEN/相关开源项目的实现，也可以从人物包或已提取图集取素材；代码借鉴须核对许可。
- 素材版权当前不考虑：原作提取图集和切好的帧可以提交进仓库和镜像，将来统一清洗。代码借鉴仍记录许可。
- 跨作品角色按各自原作像素 1:1 显示，接受 KOF 与侍魂等作品的身高差异，不做强制缩放；除非找到不损失像素质量的完美方案，再单独讨论。
- 人物优先原作像素、高质量、版本与来源明确的素材，避免重绘、滤镜放大。目前只导入了 KOF 2002 Terry 的少量动作，不能当成完整的原作角色。
- 标准 libretro core，本机静态链接、桌面动态库。先做软件渲染，规则与绘制指令隔离，保留将来其他设备/GPU 后端空间；暂不同时维护多条设备渲染路径。
- 尽量减少人工上电：先做好主机正确性回归、真实素材准备和足够的诊断，再合并成一次硬件测试。不要要求用户仅为补足本次压力测试的十分钟再次上电。
- 用户已授权实现 POC；当前仍是 P0 阶段，未完成 P1 的完整格斗系统。下一步以优化与资源验证为主，不自行扩大到联网、通用脚本或完整角色库。

前端新增 `CORE_FIGHTER` 和 `.fight` 识别，自动按后缀选择核心，使用独立游戏菜单，不加 GBA 色彩或网格效果。存档使用 `saves/<文件名含.fight>.fighter.state`，不写 `.sav`。菜单、休眠、电源和开机续玩复用宿主。`mk/image.mk` 将两个自制内容包放进新镜像的 `roms/`。

画面：480×320，核心 RGB565 优先，宿主不接受时转 XRGB8888；旋转只在前端。音频：60 Hz/48 kHz，每次 run 生成 800 个立体声采样帧，仅测试蜂鸣。核心有 port 0/1 和禁用端口支持，桌面选项 `fight_players=two`；设备前端目前只提供 port 0。

按键：方向移动/上跳，A/B/X/Y 都是同一种攻击，后方向防御，L 判定框、R 换压力、START 暂停，SELECT+START 系统菜单。无必杀、投技、Hitstop、取消、倒地系统和选人。

## 当前实现

- `app/fighter/fighter.c`：整数确定性规则，移动、跳跃、一种普通攻击、后方向防御、相打统一结算、简单 AI、KO 后自动开局。四个攻击键目前使用同一动作；尚无必杀、投技、Hitstop、取消、倒地规则和选人。
- `app/fighter/render.c`：FIGHTP05 解析，加载时把每个（帧, 调色板）组合展开成常驻 RGB565 span。矩形按行填充，人物按 span 复制（翻转时倒序复制），alpha 和 add 各有独立循环，内层没有模式分支和除法。战斗状态与绘制指令分开，后续 GPU 后端可替换合成部分；当前只实现软件路径。
- `app/fighter/libretro.c`：60 Hz、48 kHz、每次 run 800 个立体声采样帧，RGB565 优先、XRGB8888 回退；两逻辑输入端口和禁用端口，版本化小端存档，资源摘要/模式验证。桌面通过 `fight_players=two` 可用双端口，本机前端只提供 port 0。
- `.fight` 内容在前端列表直接加载，使用独立菜单与存档名，复用音频、显示、电源、休眠和开机续玩。画面不加 GBA 特效。
- 当前设备按每个 vblank 推进一个 tick，加载日志记录实际刷新率和速度比。已知屏幕约 60.02 Hz，对 60 Hz 内容约快 0.03%；POC 接受这一偏差，音频用现有动态重采样跟随显示。尚未实现严格按墙钟的 60 Hz 调度。

资源格式是 FIGHTP05，布局写在 `tools/fighter/pack.py` 开头，清单 schema 写在 `assets/fighter/README.md`。帧按实际内容裁边、尺寸可变、各带脚底锚点，按行存不透明 span 的调色板索引，调色板和帧都带图集编号。规则只给出“动作和已经过的 tick”，`fight_scene` 按包里的动画挑帧，渲染层不知道锚点。旧格式直接拒绝，不迁移。

一个包由 `assets/fighter/roster.json` 列出的多个清单组成，每个清单对应一张图集，也能单独打包测试。整个阵容的调色板索引帧常驻，开打时只把对战双方的（角色, 调色板）展开成 RGB565，加载时证明任意两人加特效都放得下。上限 32 个角色、4096 帧、每个角色 8 个必杀技和 4 种飞行道具，静态 BSS 约 23 MB（只有用到的页面占内存）。现在 7 个角色时每包约 2.8 MB，常驻内存（帧索引约 2 MiB、span 约 0.9 MiB）写进加载日志。整包打包约 40 秒（纯 Python 解 PNG）。

阵容 11 人：KOF 2002 的 Terry、Chin、Chris、Mature、May Lee、Shermie、Vice，KOF 2003 的八神庵、不知火舞，月华剑士的镜真之介（以上都是 Heatpark 提取，来自 Sprite Database），侍魂 V Special 的霸王丸（the shirt ninja 和 Firejoker54 提取，Spriters Resource 现站拒绝脚本请求，取自 Wayback Machine 存档）。来源和 SHA256 在 `assets/fighter/README.md`。原像素 1:1，站高从舞约 91 px 到真之介约 117 px。每人都有同一套基本动作和站蹲八个普通技（剑士的拳键为斩），除 Shermie 只有两招外每人有 2 到 4 个必杀技，多数带飞行道具或位移。原作指令里我们不支持的（41236、追加输入、指令投）换成最接近的 236/214/623/蓄力，或者暂不导入，记在各清单 notes。真之介的图集是一代 Boss 版，没有蹲姿和踢技，这几项是借帧凑的。所有招式数值都是估计（`src` 标为 estimate）。霸王丸镜像对局展开约 144 万像素，是最大的一对，`MAX_PIXELS` 是 2M。11 人整包约 6.2 MB。

判定和招式（P1 第 1 到 3 步）：受击框按帧给（姿势的属性，可复用另一帧，`[]` 为无敌），打击框按招式的步给，连续带打击框的步是一段，一段只命中一次。框以锚点为原点，x 朝前、y 朝下，朝左时镜像为 `x' = -(x+w)`。招式字段有 damage、chip、hitstun、blockstun、hitstop、pushback、block_pushback、guard（high/low/overhead）和 cancel；startup/active/recovery 和 reach 由加载器从步推导，`pack.py data` 打印帧数据表。时序规则写在 `fighter.c` 头注释：命中后双方冻结 hitstop 帧，推开按剩余量每帧推 1/4，被墙挡住的部分转给攻方。防御要求不在招式和受击硬直中、站在地上、按后；low 只能蹲防，overhead 只能站防。

按键与 RetroPad 一致：Y=LP，X=HP，B=LK，A=HK，按住下出蹲版，后防御，下后蹲防；L 判定框叠加，R 切压力场景，START 暂停。

输入（P1 第 4 步）：每人状态里存最近 32 帧方向，按朝向换成小键盘记法往回扫。236/214 窗口 15 帧，623 窗口 20 帧，蓄力要按住 30 帧、松开 10 帧内输入反方向；按键缓冲 4 个未冻结帧（hitstop 不计时），起跳前有 3 帧 prejump。按下时必杀技优先于普通技；自己的飞行道具还在场时跳过道具类必杀技。取消：普通技实际命中或被防，cancel 带 special 或 chain，且还没过 active 帧，取消后的招式在 hitstop 结束后第一帧开始。

Terry 的必杀技：Power Wave（236+P，第 17 帧发射地面波，伤害 70，削血 14），Burn Knuckle（214+P，13/12/15，伤害 90，带前冲位移），Rising Tackle（下蓄上+P，6/18/33，伤害 100，起手无敌）。飞行道具状态里有 4 个槽，每人同时只能有 1 个；两个道具相碰同时消失，超过寿命或出屏 64 px 消失，命中时只冻结防守方。混合模式的道具走特效预算，优先于压力场景特效。

AI 每 29 帧选一个招式走进射程出招，空闲时约 1/64 概率出必杀，约三分之二的来招会防（部分防错高度）。

游戏模式是简单的单人闯关：开局选人（方向键移光标、攻击键确认），然后依次随机打还没打败的电脑对手，一场一局（`ROUNDS_TO_WIN` 常量），HUD 显示关卡如 3/6。输了显示结果约 3 秒回选人，赢了直接下一关，全部打完显示通关画面再回选人，结果和通关画面 20 帧后可按键跳过。只有一个角色时才会镜像对局。Auto 包跳过选人，P1 按轮次轮换角色，压力场景照旧循环。桌面 `fight_players=two` 时 port 1 操作闯关的对手。

特效上限在 `fight_scene` 里：混合精灵每帧共用 76800 个不透明像素（约 12 个火柱），放不下的丢弃，只影响绘制不影响规则。每个计时窗口输出 `fight: scene N effects drawn/requested ...`。预算按首轮真机数据估计，下次上机再调。

已知待看（另见各清单 `notes` 和导入时记录的疑点：Chris 的动作归属是按位置推断的，Vice 和 Mature 的前进后退可能对调，May Lee 的站轻脚打头部高度）：站 HK/LK 按支撑的后脚对齐，出招时身体比 idle 后移约 30 px，HK 的 reach 和 LP 差不多；蹲 HK 那帧腿在中段，不太像贴地扫腿。这些需要对照原作手感调锚点或换帧。

绘制顺序：出招的一方在上层（见上面 boot-0016 的反馈）。

核心状态是 464 字节：`FGSTATE5`（水平坐标是 1/4 像素），在每人的招式、经过帧、冻结、推开余量之外，还有闯关进度（模式、计时、已打败集合、关卡、选人和配色）、输入历史、缓冲、蓄力、AI 计划和飞行道具槽；设备前端加外层校验后文件为 504 字节。旧状态被拒绝，`fight_decode` 还会按资源里的招式校验经过帧和段号。改变规则/序列化字段时要明确升级或拒绝旧状态，不要误恢复。渲染缓存不存入状态；坏存档不得部分修改现有状态。

## 主机构建与回归

本轮 `make image`、完整 `make frontend-test` 零 warning 通过，36010 帧原生长测试通过；产物 `build/sdcard.img`（128 MiB）。之后已取得首轮真机日志，结果见下文。

```sh
make fighter          # ARM64 静态核心、桌面共享核心、两个内容包
make fighter-test     # ASan/UBSan 源码测试，以及实际动态链接的同一回调测试
make frontend-test    # 完整前端回归，含 fighter 的 qemu 集成测试
make image            # build/sdcard.img，含两个 POC 内容包
```

`build/fighter/fighter_libretro.so` 可供桌面 libretro 宿主加载。已用原生回调宿主验证实际共享库加载；尚未人工运行 RetroArch。ASan/UBSan 验证源码链接版本；由于当前沙箱的 ptrace 限制，LeakSanitizer 单独关闭，未完成泄漏检测。

原生测试覆盖坏包/截断/摘要、两种像素格式、音频帧数、双端口与禁用、确定性存档和画面/声音回放、暂停、坏存档不修改状态、相打、防御、跳跃及全部压力场景。长运行测试额外核验 36000 次有效推进后只报告一次完成：

```sh
ASAN_OPTIONS=detect_leaks=0 FIGHTER_LONG_TEST=1 build/fighter/test \
  build/fighter/Fighter-POC.fight build/fighter/Fighter-Auto.fight \
  build/fighter/preview-long.ppm
```

前端回归脚本 `tools/fighter/frontend-test.sh` 覆盖后缀选核心（覆盖冲突 GBA 设置）、480×320 输出、状态保存/恢复、浅休眠、菜单重启、关机后开机恢复、退出回到子目录、四场景日志与坏包拒绝。原有 GBA、视频、核心切换和分区扩展回归照常执行。主机/QEMU 的毫秒数不能推算真机性能。

`tools/fighter/pack.py` 用纯 Python 解 PNG（每个包约 5 秒）。`detect` 列出每行候选框，`preview` 把各动作按锚点并排输出 PPM 供目视检查，`build` 按清单打包；碰到署名框、白色下划线，或矩形外圈不是纯背景（切到相邻帧）都会拒绝。判定框仍是规则里的固定值，没有逐帧判定数据。

`test-render.c` 用测试自己生成的合成包和真实包覆盖：18 种字段篡改、所有长度截断、尾部多字节、旧格式、单字节翻转全部拒绝；常驻 span 和像素与源位图逐一对照；独立写的逐像素参考渲染器在随机底图上与优化版逐像素比较，覆盖各 blend/alpha 组合、add 饱和、四边四角裁剪、翻转、无效命令、固定种子随机场景和 2400 tick 真实对战。对 render.c 人为注入的 7 种错误全部被抓到。`FIGHTER_BENCH=1 build/fighter/test-shared ...` 输出主机各场景渲染耗时。

主机 x86 每帧渲染（只看相对变化，内容也不完全相同）：场景 0 从约 450µs 降到约 14µs，+8/+24/+48 从约 770/1690/2760µs 降到约 175/455/910µs。压力场景现在几乎全是逐像素 alpha/add 混合。

前端旋转 blit（`app/frontend/blit.c`）同时改成分块转置：每 32 列一个 band，8×8 块用 NEON 转置并预取，1x 无特效路径转置到行缓冲后整行写出，缩放和特效路径先转置到列缓冲再展开。输出与旧实现逐像素一致，`selftest.c` 的 `test_blit` 与 `blit_reference` 对比的用例已扩充。Pi 5（A76）上 480×320 1x 从 0.251 降到 0.090 ms，GBA 2x 无特效约快 2.3 倍，有色彩或网格的路径基本不变（瓶颈是查表）。A35 上的收益要看下次真机日志里的 blit 计时；band 和预取距离是可调的 `BAND`、`PREFETCH_ROWS`。缓冲是 static，blit 只能在主线程调用。

## 一次上机的技术测试流程

尽量等原作素材样例也准备好后，再安排一次统一上机；以下合成测试可在同一次开机里完成。烧卡会覆盖数据分区，按现有流程备份 `saves/`。镜像在 `roms/` 放入 `Fighter-POC.fight` 和 `Fighter-Auto.fight`；已有可运行系统也可以更新前端与这两个内容，无需为素材单独重新上电。

1. 打开 `Fighter-POC`：选人后闯关。方向移动/跳跃，Y/X/B/A 为轻拳/重拳/轻脚/重脚，后方向防御，Terry 试 236/214/下蓄上 + 拳，L 判定框，R 手动换压力，START 暂停；SELECT+START 系统菜单。检查画面比例、朝向、按键和声音，试一次菜单重启、短按电源休眠/唤醒、退出再进恢复。
2. 打开 `Fighter-Auto`，在系统菜单将 CPU 设为 Max 后恢复。AI 自动对打，每 600 个模拟 tick 切场景：正常两人，额外 8、24、48 个 Power Geyser 火柱特效（alpha 160 与加法混合，平均约 6400 个不透明像素，与旧剪影工作量相近）。四场景每轮 2400 tick，满速时约 40 秒；当前重载会延长到约 70 秒。运行至少 10 分钟；慢帧和暂停会延长实际用时。
3. 同一次开机可切回 Adaptive 再跑几轮，观察是否卡顿；日志会记录实际频率。当前不会自动遍历 CPU 档位。结束后退出并正常关机，取回完整 `log/boot-NNNN/`。

不要求打开 Debug log。核心每个窗口输出逻辑/渲染/音频生成的 avg/p95/p99/max；前端每 10 秒输出 run/blit/音频提交、missed vblank、underrun、频率、温度、电量及整个进程峰值 RSS，退出写 `perf.csv` 总结。每次加载或 reset 后累计 36000 次有效逻辑推进，会写 `fight: benchmark complete`，约 15 轮；即使从旧状态恢复，也从本次加载重新累计。完成后继续运行，当前无屏幕完成提示。菜单暂停不计入有效推进，核心自身暂停时渲染窗口仍有样本。

```sh
python3 tools/fighter/report.py /path/to/log/boot-NNNN/
```

汇总工具给出各场景加权平均、各窗口 p99 的最大值与最大耗时；不会把窗口分位数冒充整个运行的 p99。分析仍需保留原始日志和 perf.csv，关联 CPU、温度与场景。初始目标是正常对战总工作 p99 <12 ms、无持续 missed vblank/underrun；高压力场景用于找到软件合成边界，不要求任意数量特效都满速。

## 首轮真机结果：boot-0015（2026-11-03）

日志来自 `build/cardlog-20261103b/log/boot-0015/frontend.txt` 和同批 `log/perf.csv`；原始日志留在忽略的 build 目录，不加入版本控制。本次只分析 boot-0015，其余为历史开机记录。

流程：手动 POC 跑了 1820 帧，期间切换过压力场景；Auto 首次 66 帧退出，再成功恢复 184 字节即时存档，继续 13620 帧。长会话按 perf 汇总约 384.2 秒有效游戏时间，其中 Adaptive 79.4 秒、Max 304.8 秒；Max 在开机约 222 秒启用。全程未达到本次加载 36000 tick，未出现十分钟完成标记。已覆盖多轮完整压力循环，足够定位当前瓶颈，无需为补满时长单独再上电；不能据此宣布十分钟稳定性验收通过。

以下仅取长会话开机 250 秒之后的 Max 窗口，避开调频和切菜单；均为**核心软件合成**，不含宿主旋转与音频输出。p99 一列是窗口 p99 的最大值，不是全会话分位数。

| 场景 | 额外精灵 | 核心合成均值 | 最大窗口 p99 | 观察到的运行速度 |
|---|---:|---:|---:|---|
| 0 | 0 | 5.49 ms | 7.53 ms | 普通双人可约 60 fps |
| 1 | 8 | 9.46 ms | 9.95 ms | 可约 60 fps，余量下降 |
| 2 | 24 | 18.74 ms | 20.68 ms | 持续超时，约 30 fps |
| 3 | 48 | 32.91 ms | 35.86 ms | 持续超时，约 20 fps |

逻辑通常约 3–5 微秒，音频生成约 4–5 微秒；宿主旋转 blit 平均约 2.9–3.0 ms，仍须加入总预算。Max 下几段完整低负载的前端 10 秒窗口有约 601 帧、missed vblank=0、underrun=0；其 run 窗口可能跨场景 0/1，不能当作严格的单场景总工作 p99。第一段游戏的 perf 帧计数还混有先前会话的残留样本，不用于此表。

高压力的慢帧同时减少每秒音频产量：核心每次 run 固定生成 800 帧，宿主每 vblank 至多调用一次，超时后逻辑和声音一起变慢，缓冲最终耗尽。长 Auto 会话共 2724 次 underrun（Adaptive 511、Max 2213）；Max 汇总 missed vblank 7647。它们集中在超时场景，正常负载窗口又恢复为零，支持“软件合成超过帧预算”这一解释，不能靠扩大音频缓冲持续补救。当前调度也没有在慢帧时维持独立 60 Hz 模拟，后续需明确过载处理策略。

峰值 RSS 始终 21920 KiB（约 21.4 MiB，包含此前 GBA 会话的整个前端进程峰值）；本轮未看到继续增长。最高采样温度 47.7°C，Max 时采样频率仍为 1296 MHz，未看到支持热降频为主因的证据。50% 背光下 Max 混合压力会话电池统计平均约 1.61 W；这是整机及场景混合值，不能当成纯正常对战功耗。

日志证明加载、正常输出、切压力、系统菜单、退出保存和再次加载恢复正常；本次没有 fighter 的电源休眠、开机续玩或重启测试记录，画面/声音的主观效果仍由用户观察确认。开机发现既有 FAT dirty bit，结束走了正常卸载路径；不是本轮格斗负载崩溃的证据。

结论：保留软件渲染路线，当前实现对两人基础场景可用，但大量混合精灵不够。下一步先定真实素材格式并导入原作人物，再按新格式做专用不透明填充/复制、透明 span 跳过和 alpha/add 热点优化，加入逐像素等价回归；暂不因合成压力失败就引入完整 GPU 栈。严格的 10 分钟稳定性、真实资源与声音延迟验收仍待完成，集中到下一次有实质改进的硬件测试。

## 后续执行顺序

1. **先定真实素材格式，再优化合成（格式和 Terry 导入已完成）。** Neo Geo 原作人物是调色板色加透明色，没有半透明；只有特效需要 alpha/add。从已有 Terry 与一个持刀型角色候选开始，记录版本/提取者/摘要，保持原像素 1:1，整理锚点与帧序；按实际帧裁掉透明边，避免把宽刀光裁掉。人物优先走透明色加按行不透明 span 的快路径，混合只留给特效。当前固定 128×160/8 姿势和逐像素 alpha 不能冒充最终角色管线，也不值得针对它做深度优化。先做动作和特效负载样例，不立刻做完整招式库。
2. **按新格式优化软件合成，并保证像素等价（span 渲染器和前端分块旋转已完成，等真机数据；剩下是 alpha/add 混合，考虑 NEON 或限制特效数量）。** 首轮 5.49 ms 基线主要是全屏背景、柱子、地面和 HUD 等不透明矩形走通用逐像素循环的开销，不代表真实角色成本：不透明填充、静态背景整行复制、精灵 span 复制和混合各用独立循环，去掉内层的 op 分支和逐像素索引运算。前端旋转约 3 ms 同样计入总预算，一并评估分块转置（GBA 与视频也受益）。先用独立标量参考实现或固定样例验证裁剪、翻转、透明、alpha/add、RGB565 舍入和饱和的逐像素结果，再测主机热点。不要用视觉相似代替等价；不要只加重复实现本身的测试。尚未选定 NEON，也没有已经写好的优化分支。

## 开发注意事项

- 构建环境里沙箱内的 fakeroot 曾报 chown Invalid argument；在沙箱外执行同一个 `make image` 后成功，无需修改 rootfs 配方。再出现时先判断执行环境。
- `tools/fighter/report.py` 会合并同一日志里所有 fighter 会话，部分 perf 总结还包含同一开机的 GBA 会话；第一段 perf 计数有前一会话残留（665 vs 600 等）。正式表格需另外按开机时间和 CPU 档位筛选窗口，p99 只能报“最大窗口 p99”。
- 原始日志、存档、配置留在被忽略的 `build/` 下，不提交；换机器时依赖本文的结果，必要时向用户索取原始日志。
- 只更新前端/核心且内核、dtb、bootloader 没变时，可以按 roadmap 的流程只更新 p2 rootfs 和 GBA 分区的内容文件，保留存档/配置/日志；设备路径与分区布局每次重新确认。写卡和上电需用户安排，不默认执行。
- 当前 fighter 日志默认开启聚合，不需要用户手动打开 Debug log。
