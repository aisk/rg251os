# 格斗引擎：POC 实现、验证和后续计划

2026-11-03。设备优先的 480×320、1 对 1、标准 libretro 软件渲染原型。当前交付用于验证核心和宿主集成；已完成首轮合成负载真机测试，普通场景可满速，高压力场景超时；P0 的持续稳定性与真实素材验收、原作素材导入以及 P1 的完整格斗规则仍待完成。设计取舍见[方案调研](fighting-engine-research.md)，数值、属性和多作品体系的设计见[数值设计](fighter-stats.md)，背景、打击效果和声音的设计见[表现层设计](fighter-presentation.md)，方案包含未来设计，实际完成范围以本文和代码为准。

## 目标和约束

- 自研拳皇式传统横版 1 对 1，以拳皇、侍魂等跨作品角色对战为方向。只需背景、共同地面与左右边界；不做平台规则，不考虑四人。
- 无需兼容 MUGEN 人物行为。可以参考 MUGEN/相关开源项目的实现，也可以从人物包或已提取图集取素材；代码借鉴须核对许可。
- 素材版权当前不考虑：原作提取图集和切好的帧可以提交进仓库和镜像，将来统一清洗。代码借鉴仍记录许可。
- 跨作品角色按各自原作像素 1:1 显示，接受 KOF 与侍魂等作品的身高差异，不做强制缩放；除非找到不损失像素质量的完美方案，再单独讨论。
- 人物优先原作像素、高质量、版本与来源明确的素材，避免重绘、滤镜放大。选角以趣味性为主，不限 SNK，射击和清版游戏的角色也可以；要求原生方形像素能 1:1 显示，CPS 系列这类非方形像素的不用，Capcom 角色走 SVC Chaos 的 Neo Geo 重画版。
- 标准 libretro core，本机静态链接、桌面动态库。先做软件渲染，规则与绘制指令隔离，保留将来其他设备/GPU 后端空间；暂不同时维护多条设备渲染路径。
- 尽量减少人工上电：先做好主机正确性回归、真实素材准备和足够的诊断，再合并成一次硬件测试。不要要求用户仅为补足本次压力测试的十分钟再次上电。
- 游戏模式以单机对 CPU 为主（Arcade 闯关、Survival、Practice），不做清版动作模式，但可以加入清版游戏的角色（见[数值设计](fighter-stats.md)）。数值以娱乐性为主，不追求平衡。不做联网和通用脚本。

前端新增 `CORE_FIGHTER` 和 `.fight` 识别，自动按后缀选择核心，使用独立游戏菜单，不加 GBA 色彩或网格效果。存档使用 `saves/<文件名含.fight>.fighter.state`，不写 `.sav`。菜单、休眠、电源和开机续玩复用宿主。`mk/image.mk` 将两个自制内容包放进新镜像的 `roms/`。

画面：480×320，核心 RGB565 优先，宿主不接受时转 XRGB8888；旋转只在前端。音频：60 Hz/48 kHz，每次 run 生成 800 个立体声采样帧，声音见下面的“表现层”。核心有 port 0/1 和禁用端口支持，桌面选项 `fight_players=two`；设备前端目前只提供 port 0。

按键：方向移动/上跳，A/B/X/Y 都是同一种攻击，后方向防御，L 判定框、R 换压力、START 暂停，SELECT+START 系统菜单。无必杀、投技、Hitstop、取消、倒地系统和选人。

## 当前实现

- `app/fighter/fighter.c`：整数确定性规则，移动、跑动和后撤步、跳跃、普通技和必杀技、防御、相打统一结算、倒地和起身、投技、AI、闯关和场景命令（规则细节写在它的头注释里，下面各段是摘要）。
- `app/fighter/render.c`：FIGHTP11 解析和渲染缓存。整个阵容的调色板索引帧常驻，RGB565 只为当前画面需要的人物和舞台按需展开（见下文渲染缓存）。矩形按行填充，人物按 span 复制（翻转时倒序复制），alpha 和 add 各有独立循环，内层没有模式分支和除法。战斗状态与绘制指令分开，后续 GPU 后端可替换合成部分；当前只实现软件路径。
- `app/fighter/libretro.c`：60 Hz、48 kHz、每次 run 800 个立体声采样帧，RGB565 优先、XRGB8888 回退；两逻辑输入端口和禁用端口，版本化小端存档，资源摘要/模式验证。桌面通过 `fight_players=two` 可用双端口，本机前端只提供 port 0。
- `.fight` 内容在前端列表直接加载，使用独立菜单与存档名，复用音频、显示、电源、休眠和开机续玩。画面不加 GBA 特效。
- 当前设备按每个 vblank 推进一个 tick，加载日志记录实际刷新率和速度比。已知屏幕约 60.02 Hz，对 60 Hz 内容约快 0.03%；POC 接受这一偏差，音频用现有动态重采样跟随显示。尚未实现严格按墙钟的 60 Hz 调度。

资源格式是 FIGHTP11（FIGHTP07 之后招式带名字，FIGHTP08 之后多了倒地动作、招式和飞行道具的倒地/追打标志、体系的起身时间，FIGHTP09 之后多了投技的两个动作和体系的投技参数，FIGHTP10 之后多了跑动和后撤步两个动作和体系的 `dash` 参数），布局写在 `tools/fighter/pack.py` 开头，清单 schema 写在 `assets/fighter/README.md`。帧按实际内容裁边、尺寸可变、各带脚底锚点，按行存不透明 span 的调色板索引，调色板和帧都带图集编号。规则只给出“动作和已经过的 tick”，`fight_scene` 按包里的动画挑帧，渲染层不知道锚点。旧格式直接拒绝，不迁移。

一个包由 `assets/fighter/roster.json` 列出的多个清单组成，每个清单对应一张图集，也能单独打包测试。整个阵容的调色板索引帧常驻，RGB565 缓存分三个区（舞台按最大舞台、两侧各按最大角色分配），加载时证明任意两人加任意舞台加特效都放得下。上限 64 个角色、256 个调色板、16384 帧、32768 个步骤、65536 个判定框、每个角色 8 个必杀技和 4 种飞行道具，帧索引上限 64 MiB、span 上限 4M 个、行上限 2M（按今天的平均体量约 48 人还有余量；23 人时帧索引约 15.3M、span 约 82 万、帧 4309、调色板 61）。帧、调色板、步骤和判定框在包里和内存里都是 16 位下标，所以这几项不能再超过 65536。`pack.py build` 最后一行 `limits:` 打印每项用量，超限时打包就报错。行、span、帧索引和 RGB565 像素这四个大数组在加载时放到堆上，读帧时按需加倍增长，最后裁到准确大小（行和 span 再加上最大舞台展开要用的部分，像素是特效加三个缓存区），`MAX_*` 只用来校验；重新加载、加载失败和卸载时都会释放。`struct assets` 剩下的固定表约 1.7 MiB 仍是静态的。这些数组不能做成静态：前端静态链接了 gpSP，它的 JIT 缓存要映射在 text 段 ±128 MB 以内，上限提高后静态 BSS 一度涨到约 114 MiB，gpSP 找不到位置就退回了解释器。现在前端 ELF 的 BSS 约 12.7 MiB（`frontend.elf` 13294168 字节，原来 130734632）。26 人的包加载后堆上约 31 MiB（帧索引约 16 MiB、span 约 6.8 MiB、行约 1.7 MiB、缓存 RGB565 约 5.9 MiB），写进加载日志。现在 7 个角色时每包约 2.8 MB，常驻内存（帧索引约 2 MiB、span 约 0.9 MiB）写进加载日志。整包打包约 40 秒（纯 Python 解 PNG）。

渲染缓存（boot-0017 卡顿的修复）：`fight_want` 只记下当前画面要谁，换人时清空对应区，不展开；选人、结果和通关画面只要 P1 一侧（练习模式选木桩时要两侧）。每次 run 先用 `fight_prefetch` 展开最多 48K 像素（舞台逐行续做，然后 P1、P2），再建场景，场景里还没展开的帧记为 miss，`fight_demand` 只补这几帧后重建场景。所以选人移一次光标只展开一个角色的当前帧加少量预取，闯关每局开头的 0.75 秒对阵卡（`INTRO_TICKS` 45，显示关卡、双方、名字和舞台名，期间规则不动，按住的键只记录不算按下）足够把整套分片展开完。主机上整套展开约 1 ms（0.49 ns/像素），单次 run 最多约 5.7 万像素，按真机旧数据（约 20 ns/像素）估 1.2 ms，600 MHz 约 1.7 ms。输出与一次性全部展开逐像素相同（`test-render.c` 用选人移光标和 9000 帧 Auto 对比）。缓存不进存档；对战中读档会阻塞地一次展开并记日志。日志：每次填满记 `fight: cast A vs B on 舞台 ready in N runs`（像素、缓存总耗时和单次最大耗时、按需帧数、被取代的次数、各区常驻大小），场景计时多一项 cache。

阵容 29 人（后加入的 18 人见下面第 5 项的导入记录），最早的 11 人是：KOF 2002 的 Terry、Chin、Chris、Mature、May Lee、Shermie、Vice，KOF 2003 的八神庵、不知火舞，月华剑士的镜真之介（以上都是 Heatpark 提取，来自 Sprite Database），侍魂 V Special 的霸王丸（the shirt ninja 和 Firejoker54 提取，Spriters Resource 现站拒绝脚本请求，取自 Wayback Machine 存档）。来源和 SHA256 在 `assets/fighter/README.md`。原像素 1:1，站高从舞约 91 px 到真之介约 117 px。每人都有同一套基本动作和站蹲八个普通技（剑士的拳键为斩），除 Shermie 只有两招外每人有 2 到 4 个必杀技，多数带飞行道具或位移。原作指令里我们不支持的（指令投、蓄力释放）换成最接近的指令，或者暂不导入，记在各清单 notes；半圈和 421 现在支持了，2026-11-04 已把相关招式改回原作指令（见第 6 项）。真之介的图集是一代 Boss 版，没有蹲姿和踢技，这几项是借帧凑的。招式数值原本都是估计（`src` 标为 estimate），其中一部分 2026-11-04 改成了有出处的原作数据。霸王丸镜像对局展开约 144 万像素，是最大的一对，`MAX_PIXELS` 是 2M。11 人整包约 6.2 MB。2026-11-04 又加了 7 人：SVC Chaos 的色、Zero、火星人（kilburto 的 Spriters Resource 索引图，用户手动下载，帧序锚点判定参考 KOF EXUM 的 MUGEN 包），侍魂 V Special 的莉姆露露，Waku Waku 7 的 Arina 和 Politank-Z，Rage of the Dragons 的 Sonia。站高从 Zero 约 87 px 到 Politank-Z 约 128 px。新人的指令、帧数据和伤害同样多为估计。色、莉姆露露和 Arina 的语音取自 MUGEN 包（见 `assets/fighter/sound/README.md`），Politank-Z 和 Sonia 找不到声音来源，只有通用音效。18 人整包约 11.3 MB，调色板索引帧常驻约 8.3 M 个，`MAX_INDICES` 提到 1<<24。各角色与原作数据的差距和可加的机制，调查结果在本机 `build/fighter/source/MECHANICS.md`（不提交）。之后又加了 KOF 2003 的怒号队 Ralf 和 Clark（Heatpark 图集，Sprite Database），站高约 108 px。普通技的出招和被防帧差按 franckfrost 的 KOF 2002 UM 表；必杀技用 KOF 2002 的指令，Ralf 有 Gatling Attack（[4]6+P）、急降下爆弾 Punch（[2]8+P）、Ralf Kick（63214+K）和 Vulcan Punch（原作连打 P，引擎不读连打，换成 236+P）；Clark 是投技角色，指令投做不了，Napalm Stretch（623+P）、Frankensteiner（623+K）、Mount Tackle（41236+P）都用落空动画改成打击技，Super Argentine Backbreaker 等指令投不导入。伤害、推开和空中招式的轨迹是估计。两人没有 MUGEN 包可参考，也没有语音。

判定和招式（P1 第 1 到 3 步）：受击框按帧给（姿势的属性，可复用另一帧，`[]` 为无敌），打击框按招式的步给，连续带打击框的步是一段，一段只命中一次。框以锚点为原点，x 朝前、y 朝下，朝左时镜像为 `x' = -(x+w)`。招式字段有 damage、chip、hitstun、blockstun、hitstop、pushback、block_pushback、guard（high/low/overhead）和 cancel；startup/active/recovery 和 reach 由加载器从步推导，`pack.py data` 打印帧数据表。时序规则写在 `fighter.c` 头注释：命中后双方冻结 hitstop 帧，推开按剩余量每帧推 1/4，被墙挡住的部分转给攻方。防御要求不在招式和受击硬直中、站在地上、按后；low 只能蹲防，overhead 只能站防。

按键与 RetroPad 一致：Y=LP，X=HP，B=LK，A=HK，按住下出蹲版，后防御，下后蹲防，66 跑动、44 后撤步；L 判定框叠加，R 切压力场景（练习模式对战中切木桩行为），START 暂停（显示出招表），暂停时按 B 回选人；选人界面里 L 切游戏模式，START 开关当前光标角色的出招表，R 切换 CPU 难度。

出招表：暂停时把画面压暗，在面板里列出 P1 角色的指令；选人界面按 START 换成左边角色立绘、右边出招表的布局，方向键照样换人。表由 `fight_move_list` 从包里的招式数据生成，不写死：先按包里的顺序列出没有父招式的必杀技，再列有追加招的普通技，每一项下面缩进列出它的追加招（最多三层，前面画一个 >）。指令用 HUD 字体新加的 5×5 箭头按面朝右的方向画（↓↘→ + P 这种，蓄力写成 [↓]↑ + P），按键两个拳都算写 P、两个脚写 K，否则写 LP/HP/LK/HK，武器的拳键写 S、LS、HS；后面附上包里能看出来的标签：PROJECTILE（发飞行道具）、LOW、OVERHEAD、ON CONTACT（父招式要打中或被防才能接）。最后是普通技的按键图例和蹲、跳、防御。每个必杀技有名字（清单招式的 `name`，没写就用键名，最多 16 个字符，打包时转大写，FIGHTP08 起进包）：暂停面板宽，名字（白色）一列、指令和标签（浅绿）在最长名字之后对齐成第二列；选人面板窄，名字一行、指令缩进写在下一行。名字按各清单 notes 和机制调查里的原作招式名填（日文用罗马字，较长的有缩写，如 Chris 的 Dancer Thrust/Step、Chin 的 Kuutotsu Ken），是按当前清单对招式的认定填的，招式被重新认定时名字也要跟着改。测试检查所有角色的表都在两个面板以内。字体同时加了 + [ ] > . 几个符号。

输入（P1 第 4 步）：每人状态里存最近 32 帧方向，按朝向换成小键盘记法往回扫。236/214 窗口 15 帧，623、421 和半圈（41236、63214，只认 4、2、6 三个关键方向）窗口 20 帧，蓄力要按住 30 帧、松开 10 帧内输入反方向；半圈同时也满足它结尾的 236/214，所以清单里半圈必须排在共用按键的 236/214 之前，`pack.py` 会拒绝反过来的顺序。按键缓冲 4 个未冻结帧（hitstop 不计时），起跳前的 prejump 由体系给（KOF 4 帧，侍魂 1 帧）。按下时必杀技优先于普通技；自己的飞行道具还在场时跳过道具类必杀技。取消：普通技实际命中或被防，cancel 带 special 或 chain，且还没过 active 帧，取消后的招式在 hitstop 结束后第一帧开始。

追加输入（rekka）：必杀技可以写 `after`（接在哪个招式后）、`window`（父招式经过帧的开闭区间）和可选的 `contact`（父招式要命中或被防）。追加招只在父招式进行中、到窗口结束前优先匹配，指令必须在父招式开始之后输入（状态里每人多一个 `clock`，记父招式开始后的 tick，冻结也计）；除了 236/214 等，还能用按键时按住的方向（5/8/2/6/4）或 `any`。按早了进缓冲，父招式显示到窗口内的第一个未冻结帧开始；父招式结束后缓冲里的追加招作废，追加招不会单独出。八神庵的葵花拆成三段（214+P 连按三次，一二段不接时 35 帧，窗口 9 到 14，空振也能接，第三段是中段 overhead）；May Lee 的龙尾脚（236+K）之后在窗口 19 到 33 按 K，上为双升脚、下为虎尾脚、其他方向或不按为心突脚，这三招以前被换成独立的 623/214/[4]6+K。AI 每个招式最多计划一次追加，命中或被防后必接，空振时一半概率接。窗口长度和葵花第三段是中段都是我们的估计。

Terry 的必杀技：Power Wave（236+P，第 17 帧发射地面波，伤害 70，削血 14），Burn Knuckle（214+P，13/12/15，伤害 90，带前冲位移），Rising Tackle（下蓄上+P，6/18/33，伤害 100，起手无敌）。飞行道具状态里有 4 个槽，每人同时只能有 1 个；两个道具相碰同时消失，超过寿命或出屏 64 px 消失，命中时只冻结防守方。混合模式的道具走特效预算，优先于压力场景特效。

AI 每 29 帧选一个招式走进射程出招，空闲时约 1/64 概率出必杀，约三分之二的来招会防（部分防错高度）。这是 Normal 难度，和以前完全一样。

难度：状态里存一个 `level`，选人界面按 R 在 Easy、Normal、Hard 之间循环（设备前端的游戏菜单没有核心选项，这是机器上唯一的切换办法；SELECT 不用，因为 SELECT+START 是系统菜单，先按下的 SELECT 会被误算）。核心选项 `fight_difficulty`（easy/normal/hard，默认 normal）是初始值：载入和重置时写进状态，之后只有选项本身变了、且在选人界面时才再写一次，所以 R 选的难度在选项不变时一直保留。一轮闯关打到底都是开始时的难度，读进来的对战中存档保留自己的难度，重放和读档都确定。选人界面右上角显示 CPU EASY/NORMAL/HARD，左边一个灰色的 R 提示按键；对阵卡右上角也显示难度。对战中 R 照旧切压力场景。`fighter.c` 的 `levels` 表决定 AI：

| | Easy | Normal | Hard |
|---|---|---|---|
| 防御（每 32 次来招） | 14，其中 6 次防错高度 | 22，4 次错 | 28，1 次错 |
| 防御反应 | 来招或飞行道具出来 4 tick 后才会防 | 立即 | 立即 |
| 空闲时出必杀 | 约 1/128 每 tick | 1/64 | 1/24 |
| 射程内按普通技 | 1/16 每 tick | 1/8 | 1/4 |
| 追加招 | 命中或被防后一半，空振 1/4 | 命中或被防后必接，空振一半 | 命中或被防后必接，空振不接 |
| 普通技命中后取消成必杀 | 不会 | 不会 | 3/4 的机会（只用 236/214/623 类指令，hitstop 里输入） |
| 跑动接近（8 个计划窗口里的个数，距离超过 180 px 时） | 1 | 3 | 5 |
| 后撤步（32 次近身来招里，在不防的那些里面） | 2 | 4 | 3 |
| CPU 伤害 | 75% | 100% | 100% |

伤害倍率只对闯关的 CPU（port 1 不是玩家、也不是 Auto）生效，按招式伤害先乘倍率再乘防御方的防御倍率，各自四舍五入。主机上 Auto 对打 30000 tick 的对比（`test.c` 打印）：防住的接触 Easy 约 14%、Normal 约 44%、Hard 约 53%，必杀 74/112/290 次，Hard 取消 109 次（加了跑动和后撤步之后，没防的来招有一部分改成后撤，防住的比例比以前低）。日志：载入行带难度，选项改动写进状态时写 `fight: difficulty X`，选人界面按 R 改的写 `fight: difficulty X (select screen R)`，每次 KO 和每 600 帧的汇总也带难度。设备前端的游戏菜单目前没有核心选项（音量选项也没有），所以机器上用 R 切换。

Arcade 模式是简单的单人闯关：开局选人（方向键移光标、攻击键确认），然后依次随机打还没打败的电脑对手，每场三局两胜（`ROUNDS_TO_WIN` 常量，见下面的回合计时），HUD 显示关卡如 3/6。输了显示结果约 3 秒回选人，赢了直接下一关，全部打完显示通关画面再回选人，结果和通关画面 20 帧后可按键跳过。每局开头有 0.75 秒对阵卡（`INTRO_TICKS`），接着在舞台上显示约 0.6 秒的大字 READY（`READY_TICKS`），这两段规则都不动、AI 不出手，按住的键只记录不算按下；然后显示 FIGHT（`FIGHT_TICKS`，约 0.4 秒，此时已经开打）并播开场音效。所以从选人或对阵卡一直按住的键在 FIGHT 出现时不会出招，只有新按下的才算。大字用 HUD 的 3×5 字形放大到每点 10 像素，带暗色投影。只有一个角色时才会镜像对局。Auto 包跳过选人，P1 按轮次轮换角色，压力场景照旧循环。桌面 `fight_players=two` 时 port 1 操作闯关的对手。

选人网格：每行 4 格（宽 108 像素，放得下 12 个字符的名字），一屏 8 行共 32 人，区域是 y 32 到 167，下面的立绘头顶约在 y 172。人数超过 32 时只画窗口里的行，窗口跟着光标滚动：光标所在行尽量放在第 4 行，到头尾就贴边；上面或下面还有行时，网格右侧对应的那一行旁边显示灰色的上或下箭头。窗口位置每帧由光标算出（`fight_grid_top`），不进状态。左右键在整个名单里前后移动并循环，上下键保持列并在首行和末行之间循环，末行不满时没有的那一列落到最后一个人（`fight_grid_move`）。练习模式选木桩时同一个网格，窗口跟着木桩光标，P1 的绿框滚出窗口就不画。结果、通关和对阵卡只显示单个名字，不受人数影响。一屏 32 个 12 字符的名字约要 3500 条绘制命令（一个字形最多 9 个矩形），所以每帧命令上限 `COMMANDS` 从 2048 提到 4096。

游戏模式（选人界面按 L 循环，左上角显示灰色 L 加模式名，状态里存 `game`）：
- Arcade：上面的闯关。
- Survival：选人后连续打随机对手（不会连着两场同一人），每场一局，P1 的血量带到下一场，每赢一场回复满血的 `SURVIVAL_HEAL`（150‰），不超过满血；平局（双 KO 或时间到时血量比例相同）时用带进来的血量重打这一场，输了显示 SURVIVAL OVER、本次胜场和本次开机的最高纪录，然后回选人。HUD 和对阵卡显示 WINS N，选人界面在模式名后显示 BEST N（最多 9999）。
- Practice：先选 P1，再选木桩（标题变成 DUMMY，P1 绿框、木桩青框，两人立绘对面站），任何角色都可以，不算闯关。对战中按 R 在 STAND、CROUCH、GUARD ALL（站着防高、蹲着防低）、CPU 之间切换木桩，HUD 中间显示 R DUMMY X。血量最低到 1，不会 KO，连段结束时双方回满；双方各自最近一次连段的总伤害显示为 DAMAGE N，连段计数照旧。
- 暂停时按 B 回选人（三个模式都可以）。

回合计时和三局两胜（Arcade 和 Survival）：每局 99 个计数，每个 60 tick（`CLOCK_COUNTS`、`COUNT_TICKS`），对阵卡和 READY 期间不走，FIGHT 起开始倒数，暂停时停住，画在中间的小框上，最后十个变红。时间到时双方都站着，按各自血量占自己满血的比例判胜（相同算平局），播输家的 KO 音效（平局不播）并显示 TIME UP。Arcade 每关三局两胜（`ROUNDS_TO_WIN` 2），名字和中间标签之间各有两个方块，赢一局点亮一个；平局双方各得一分，同时到两分算 P1 输（必须正面赢下）；第二局起不再显示对阵卡，READY 换成 ROUND N，双方回满血、计时重置。Survival 仍然每个对手一局（血量要带下去，打三局不好算），但同样有计时，时间到按比例判。Practice 没有计时。Auto 包为了保持轮换速度仍是一局定胜负，但有计时。`fight_start`（测试和压力场景）没有计时。日志的 KO 行改为 `fight: KO|time over stage N round N (bout B, W0-W1, clock C) ...`。
日志：切模式写 `fight: game X (select screen L)`，切木桩写 `fight: practice dummy X`，每次离开对战写 `fight: X run over (lost/cleared/quit) after N rounds, W wins, best B`；KO 行和 600 帧汇总带模式和胜场。

连段计数：没被防住的命中（打击或飞行道具）落在仍处于受击硬直的对手身上时接着计数，否则从 1 重新算；对手离开受击硬直的那一 tick 结束时连段结束。真连才算，防住或对手已经能动都会断。从第二下起在攻方名字下面显示黄色的“N HITS”，连段进行中一直显示，结束后再留 `COMBO_TICKS`（60 tick，约 1 秒），中间只有单下命中不会延长。计数上限 99。状态里每方记 `combo`（进行中的计数）、`shown`/`show`（屏幕上的数和剩余时间）和 `best`（本局最长连段），换局清零。日志：每次 KO 写一行 `fight: KO stage S round R A vs B life x/y, max combo m/n`，每 600 帧的汇总行也带当前这一局的 max combo。

倒地和起身（P1 第 5 步的一半）：招式和飞行道具带倒地标志。清单可以写 `knockdown`（true/false），没写时扫腿（蹲 HK）和所有 class 为 special/super、有打击框、不发飞行道具、后面也没有追加招的必杀技会倒地（所以葵花一二段不倒、第三段倒，May Lee 的龙尾脚不倒、三个分支倒，Power Wave 不倒），飞行道具默认不倒。多段的招式只有最后一段倒地。没防住的倒地命中、对手没被 KO 时不进受击硬直而是倒地：FALLING 播倒下动画（推开照常，空中被打就照常下落），动画放完且落地后转 LYING，先躺 `wakeup - getup` 帧，再播起身动画，LYING 满 `max(wakeup, getup)` 帧的那一 tick 就能行动。`wakeup` 是体系参数（systems.json，kof2002 和 samsho5sp 都是 25，按调查里 KOF 02 Terry 落地到能动 25 帧，其他人 21 到 31 帧，侍魂没有数据，暂用同值），以后可以按角色覆盖。倒地期间打击和飞行道具都打不到（飞行道具穿过去），只有带 `otg` 标志的招式能打躺着、还没开始起身的人，现在没有招式带这个标志。倒地时按键照常进缓冲，所以起身最后 4 帧内按的键在起身那一 tick 出招（起身反击）。KO 仍然播 KO 动画。

动作多了 `fall`、`down`、`getup` 三个，清单可以自己给，没给时由 `pack.py` 生成：fall 是 KO 动画去掉最后一步，down 是 KO 的最后一帧（躺倒），getup 是蹲姿第一帧 10 帧。2026-11-04 起 18 人的清单都从图集切了这三个动作：fall 多数就是 KO 帧重新定时（约 22 到 30 帧），down 是躺倒帧加一个贴地受击框（留给以后的追打），getup 是图集里的起身帧（有 MUGEN 包的按 5120 动作对照，总长 17 到 24 帧，不超过 `wakeup`，所以倒地总时长仍是 25 帧）。fall 和 getup 没有受击框。帧的行号、锚点来源和时长写在各清单 notes。

AI：对手倒地时不出必杀、不按普通技，只走到计划的普通技射程内等着；Normal 和 Hard 在对手还剩不超过“该普通技起手帧 + 1”帧起身时按下，让攻击压在起身上（Easy 不这么做）。自己倒地时不输入。主机上 AI 对打 30000 tick 约 79 次倒地，其中约 56 下命中落在对手起身后 4 tick 内。

投技（P1 第 5 步的另一半，按 KOF 2002 的通常投）：站在地上、没有出招和硬直时，前或后（只认正 6 和正 4，斜下是蹲重拳脚）加 HP 或 HK，如果这一 tick 开始时对手在投范围内而且可投，就在按下的这一 tick 抓住（第 1 帧生效，比同一 tick 出的打击优先，双方同时投互相拆掉）；不在范围就照常出站 HP/HK。范围是两人体距（两人 push 的较大值）再加体系的 `range`（kof2002 为 4 px，取自调查里 MUGEN EXUM 包的代理值）。不可投：空中、起跳准备、受击和防御硬直、倒地、正在投或被投，以及“安全帧”内：倒地起身后 `wakeup_safe` 帧（kof2002 为 8），硬直结束后 `stun_safe` 帧（kof2002 为 0，samsho5sp 都是 17）。被抓的一方面朝投者站在体距处，双方播 THROW/THROWN，期间什么都打不到、也不推开。被抓后 `tech` 帧内（kof2002 为 6，没有公开帧数，是估计值；samsho5sp 为 0，不能拆）按 HP 或 HK 就拆投：双方都进 `tech_stun`（12）帧防御姿势硬直，各自后滑 `tech_push`（24）px。没拆的话，投者的 THROW 动画放完那一 tick 放手：被投者吃体系的投技伤害（kof2002 为 100，约等于 SVC 的 24/224；samsho5sp 写 220，按 800 缩放后 176，即 125 血里的 22），不可防，倒地；后投先把对手挪到身后再往另一边摔。投技伤害也吃 Easy 的 75% 和防御力。参数都在 systems.json 的 `throw` 对象，字段说明在 `tools/fighter/pack.py` 开头；现在按体系，不按角色（侍魂两人的范围原作是 16 和 12，这里统一 12）。

投技动画：清单可以给 `throw`（投者，动画放完那一 tick 放手，所以以抛出或收势结束）和 `thrown`（被抓者原地的受抓姿势，第一个受击框中心是投技火花的位置）；没给时 `pack.py` 生成通用抓取：`throw` 为站 HP 的帧（不带打击框），第一帧有效帧拉长到总长至少 30 帧，`thrown` 用受击动画。2026-11-04 切了图集里的投技：Terry（Grasping Upper）、Chin、Chris、Mature、Shermie（德式背摔的前半）、Vice、Iori、霸王丸、莉姆露露、真之介（借炎咆哮的身体帧，没有爆炸）、色、Zero、火星人、Arina（踢投）和 Sonia，总长 30 到 40 帧。May Lee、舞和 Politank-Z 的投技还是通用抓取：前两人的原作投技要跳到对手身上或身后，被抓者站在前方不动时画不出来，Politank-Z 没有像通常投的行。`thrown` 只有真之介和 Politank-Z 仍用受击动画（图集没有受抓帧），其余用原作的受抓或腹部受击帧。我们的投技总是向前摔，所以向后摔的投技（Terry 的 Buster Throw、Iori 的后投等）没用。投者在空中或骑在对手身上的投技（Chin、Chris、火星人）放手时直接回到站立，会有一跳。

AI 和投技：Easy/Normal/Hard 分别有 1/2/3 成（8 个计划窗口里的个数）的计划改为投：对手没倒地时走进投范围，用 HP 或 HK 前投（偶尔后投）。被抓时按难度决定是否拆（每次投决定一次，32 里 6/12/20 次），在被抓后第 4/3/2 帧按 HP。主机上 AI 对打 30000 tick 约 43 次投成、50 次拆掉（含双方同时投）。日志：每 600 帧的汇总行和每次 KO 都带 `throws`/`techs` 计数，加载时体系那行带投技参数。

跑动和后撤步（按调查第三部分）：在地上空闲时（不在出招、硬直、起跳准备中）快速按两下前（66）开始跑，按两下后（44）后撤步。两下之间必须松开该方向，第二下要在第一下之后 `window` tick 内（10，估计值），只认正前和正后。参数在 systems.json 的 `dash` 对象，按体系不按角色，字段说明在 `tools/fighter/pack.py` 开头。
- 跑动：KOF 2002 是 3/10~/3。开始的 `run_startup`（3）tick 用走速，之后用跑速，跑速是角色走速乘 `run_scale`（2100‰，KOF EXUM 的 MUGEN 移植跑速约为走速的 2 到 2.5 倍，Terry 6.17 对 3.06），所以每个角色跑得不一样快（Terry 25，即每 tick 6.25 px）。至少跑 `run_startup + run_min`（3+10）tick，之后松开前就滑步 `run_stop`（3）tick 停下，速度递减。跑动中按攻击键或必杀指令直接出招（取消跑动），按上直接起跳，不能防御，也不能投（跑着按前加 HP 出的是站 HP）。侍魂体系可以按住一直冲，松开后还有 `run_grace`（3）tick 惯性，这期间再按前继续跑；跑速 2700‰（霸王丸走速 9，跑 24，原作 6.25 px），起手和滑步长度是估计。
- 后撤步：KOF 2002 是 3/18/3，先在地上 `backdash_startup`（3）tick，再在空中 `backdash_air`（18）tick 按抛物线后退 `backdash_distance`（72 px）、最高 `backdash_height`（16 px），落地 `backdash_stop`（3）tick。整个后撤步不能被投、不能防御，但能被打（打中就从空中落下，和空中被打一样）；侍魂体系第一帧就离地，空中 20 tick、落地 6 tick（霸王丸原作 26 帧，21 帧起落地），前 `backdash_invuln`（2）tick 打击打不到。距离和高度都是估计。离地时发 JUMP 声音事件，落地发 LAND。

## 一次上机的技术测试流程

尽量等原作素材样例也准备好后，再安排一次统一上机；以下合成测试可在同一次开机里完成。烧卡会覆盖数据分区，按现有流程备份 `saves/`。镜像在 `roms/` 只放 `Fighter.fight` 和同名的声音文件 `Fighter.fightsnd`（构建产物 `build/fighter/Fighter-POC.*` 改名拷入，核心按内容包的文件名找声音文件）。Auto 包（AI 自动对打加四个压力场景循环）只用于主机测试，2026-11-04 起不再随镜像分发；需要上机测极限负载时临时把 `build/fighter/Fighter-Auto.fight` 和 `.fightsnd` 拷到卡上，或在 `Fighter.fight` 里按 R 手动切压力场景。已有可运行系统也可以只更新 p2 和这两个文件。

1. 打开 `Fighter`：选人后闯关。方向移动/跳跃，Y/X/B/A 为轻拳/重拳/轻脚/重脚，后方向防御，Terry 试 236/214/下蓄上 + 拳，L 判定框，R 手动换压力，START 暂停（看出招表，B 回选人），选人时 L 切模式、START 开关出招表、R 切难度；练习模式里 R 切木桩；SELECT+START 系统菜单。检查画面比例、朝向、按键和声音，试一次菜单重启、短按电源休眠/唤醒、退出再进恢复。
2. （需要时）临时拷入 `Fighter-Auto` 后打开，在系统菜单将 CPU 设为 Max 后恢复。AI 自动对打，每 600 个模拟 tick 切场景：正常两人，额外 8、24、48 个 Power Geyser 火柱特效（alpha 160 与加法混合，平均约 6400 个不透明像素，与旧剪影工作量相近）。四场景每轮 2400 tick，满速时约 40 秒；当前重载会延长到约 70 秒。运行至少 10 分钟；慢帧和暂停会延长实际用时。
3. 同一次开机可切回 Adaptive 再跑几轮，观察是否卡顿；日志会记录实际频率。当前不会自动遍历 CPU 档位。结束后退出并正常关机，取回完整 `log/boot-NNNN/`。

不要求打开 Debug log。核心每个窗口输出逻辑/渲染/音频生成的 avg/p95/p99/max；前端每 10 秒输出 run/blit/音频提交、missed vblank、underrun、频率、温度、电量及整个进程峰值 RSS，退出写 `perf.csv` 总结。每次加载或 reset 后累计 36000 次有效逻辑推进，会写 `fight: benchmark complete`，约 15 轮；即使从旧状态恢复，也从本次加载重新累计。完成后继续运行，当前无屏幕完成提示。菜单暂停不计入有效推进，核心自身暂停时渲染窗口仍有样本。

```sh
python3 tools/fighter/report.py /path/to/log/boot-NNNN/
```

汇总工具给出各场景加权平均、各窗口 p99 的最大值与最大耗时；不会把窗口分位数冒充整个运行的 p99。分析仍需保留原始日志和 perf.csv，关联 CPU、温度与场景。初始目标是正常对战总工作 p99 <12 ms、无持续 missed vblank/underrun；高压力场景用于找到软件合成边界，不要求任意数量特效都满速。

## 首轮真机结果：boot-0015（2026-11-03）

日志来自 `build/cardlog-20261103b/log/boot-0015/frontend.txt` 和同批 `log/perf.csv`；原始日志留在忽略的 build 目录，不加入版本控制。本次只分析 boot-0015，其余为历史开机记录。

流程：手动 POC 跑了 1820 帧，期间切换过压力场景；Auto 首次 66 帧退出，再成功恢复 184 字节即时存档，继续 13620 帧。长会话按 perf 汇总约 384.2 秒有效游戏时间，其中 Adaptive 79.4 秒、Max 304.8 秒；Max 在开机约 222 秒启用。全程未达到本次加载 36000 tick，未出现十分钟完成标记。已覆盖多轮完整压力循环，足够定位当前瓶颈，无需为补满时长单独再上电；不能据此宣布十分钟稳定性验收通过。

以下仅取长会话开机 250 秒之后的 Max 窗口，避开调频和切菜单；均为**核心软件合成**，不含宿主旋转与音频输出。p99 一列是窗口 p99 的最大值，不是全会话分位数。

| 场景 | 额外精灵 | 核心合成均值 | 最大窗口 p99 | 观察到的运行速度 |
|---|---:|---:|---:|---|
| 0 | 0 | 5.49 ms | 7.53 ms | 普通双人可约 60 fps |
| 1 | 8 | 9.46 ms | 9.95 ms | 可约 60 fps，余量下降 |
| 2 | 24 | 18.74 ms | 20.68 ms | 持续超时，约 30 fps |
| 3 | 48 | 32.91 ms | 35.86 ms | 持续超时，约 20 fps |

逻辑通常约 3–5 微秒，音频生成约 4–5 微秒；宿主旋转 blit 平均约 2.9–3.0 ms，仍须加入总预算。Max 下几段完整低负载的前端 10 秒窗口有约 601 帧、missed vblank=0、underrun=0；其 run 窗口可能跨场景 0/1，不能当作严格的单场景总工作 p99。第一段游戏的 perf 帧计数还混有先前会话的残留样本，不用于此表。

高压力的慢帧同时减少每秒音频产量：核心每次 run 固定生成 800 帧，宿主每 vblank 至多调用一次，超时后逻辑和声音一起变慢，缓冲最终耗尽。长 Auto 会话共 2724 次 underrun（Adaptive 511、Max 2213）；Max 汇总 missed vblank 7647。它们集中在超时场景，正常负载窗口又恢复为零，支持“软件合成超过帧预算”这一解释，不能靠扩大音频缓冲持续补救。当前调度也没有在慢帧时维持独立 60 Hz 模拟，后续需明确过载处理策略。

峰值 RSS 始终 21920 KiB（约 21.4 MiB，包含此前 GBA 会话的整个前端进程峰值）；本轮未看到继续增长。最高采样温度 47.7°C，Max 时采样频率仍为 1296 MHz，未看到支持热降频为主因的证据。50% 背光下 Max 混合压力会话电池统计平均约 1.61 W；这是整机及场景混合值，不能当成纯正常对战功耗。

日志证明加载、正常输出、切压力、系统菜单、退出保存和再次加载恢复正常；本次没有 fighter 的电源休眠、开机续玩或重启测试记录，画面/声音的主观效果仍由用户观察确认。开机发现既有 FAT dirty bit，结束走了正常卸载路径；不是本轮格斗负载崩溃的证据。

结论：保留软件渲染路线，当前实现对两人基础场景可用，但大量混合精灵不够。下一步先定真实素材格式并导入原作人物，再按新格式做专用不透明填充/复制、透明 span 跳过和 alpha/add 热点优化，加入逐像素等价回归；暂不因合成压力失败就引入完整 GPU 栈。严格的 10 分钟稳定性、真实资源与声音延迟验收仍待完成，集中到下一次有实质改进的硬件测试。

9. **以后的优化方向：音乐实时合成（2026-11-04 记下，暂不做）**。现在的音乐是离线把 VGM 渲染成 MP2 再播放，等于播录音。更像真机的做法是在核心里模拟 YM2610（FM、SSG、ADPCM-A/B），直接回放 VGM 的寄存器写入，可选 ymfm（BSD）或 libvgm 的芯片核心。好处是音色和原作逐样本一致、循环无缝，还能按声道静音或变速。代价是体积省不了多少（KOF 2002 的 VGM 包 32 首约 8.3 MB，大部分是 ADPCM 采样），CPU 要实测（FM 按 55.5 kHz 逐样本模拟，A35 上估每帧 1 到 4 ms，现在 MP2 约 0.55 ms），读档要序列化芯片状态，跳转要快照。做之前先在主机用 ymfm 回放一首 KOF 2002 VGM 测耗时，再上真机，每帧 2 ms 以内才值得换，MP2 留作后备。

## 开发注意事项

- 构建环境里沙箱内的 fakeroot 曾报 chown Invalid argument；在沙箱外执行同一个 `make image` 后成功，无需修改 rootfs 配方。再出现时先判断执行环境。
- `tools/fighter/report.py` 会合并同一日志里所有 fighter 会话，部分 perf 总结还包含同一开机的 GBA 会话；第一段 perf 计数有前一会话残留（665 vs 600 等）。正式表格需另外按开机时间和 CPU 档位筛选窗口，p99 只能报“最大窗口 p99”。
- 原始日志、存档、配置留在被忽略的 `build/` 下，不提交；换机器时依赖本文的结果，必要时向用户索取原始日志。
- 只更新前端/核心且内核、dtb、bootloader 没变时，可以按 roadmap 的流程只更新 p2 rootfs 和 GBA 分区的内容文件，保留存档/配置/日志；设备路径与分区布局每次重新确认。写卡和上电需用户安排，不默认执行。
- 当前 fighter 日志默认开启聚合，不需要用户手动打开 Debug log。
